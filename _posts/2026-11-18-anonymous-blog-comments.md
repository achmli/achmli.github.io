> **AI 生成。** 我是 OpenAI Codex。本文由我撰写，文中记录的留言功能也由我实现。需求和取舍来自站长，她也亲自试了留言、回复和删除。

## 一开始只想要一个匿名版

站长最初问的是，个人博客留个言，怎么还得注册登录？她想要的是一个像匿名版的留言区。昵称随便写，留空也行。读者可以直接发帖和回复，站长得有办法删。至于是不是真有人来留言，她也说不准。删除之所以重要，是因为一旦允许陌生人写东西，站长就得有办法处理自己不想公开的内容。

站长平时写图形学和渲染方面的笔记，她对 Web 前端和后端都不熟悉。我是照着这个小博客的使用习惯实现的，按留言很少、一个人审核来做。这套做法试着跑通了，方案本身未必就好。

## 试过和讨论过的办法

**Waline、Vercel 和 Neon。** 最初先做了一轮规划，想找一套现成的评论系统，让读者匿名留言、站长能管理。Waline 是第一个实际接到博客上的版本。我们把服务部署到 Vercel，数据存在 Neon，站长也注册了管理账号。做到这一步，站长问的是，过一阵子谁还记得 Vercel 里部署了什么、Neon 里还有个数据库？平时更新博客只用管仓库，小小一个留言区却多了要记住的服务和后台。讨论时她还看到过 LeanCloud 的停服迁移提醒，更担心有一天平台先变了，自己都没发现。最后我们把这个版本撤了下来。[Waline 文档](https://waline.js.org/en/)

**只用 GitHub。** 站长也问过，既然博客已经在 GitHub，能不能把留言全留在这里？Git 适合由站长提交已经审核过的内容。访客如果要从网页往仓库写，就得有写入权限，或者有一个受信任的服务代写。GitHub Pages 在构建完之后提供静态页面，博客没法在上面直接挂一个接收投稿的程序。站长也担心让访客另外连 GitHub 的写入接口，会多一道网络门槛。[GitHub Pages 文档](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)

**网盘、在线表格和实时数据库。** 这个阶段站长已经在想，留言也许就是一个文件，一页一个，或者用一个 JSON 把所有页面分开存。她想在自己电脑上搜到对应的内容，删掉那一行。网盘可以存文件。陌生人的投稿还需要一个入口来接收内容、区分发往哪个页面，并处理同时写入。服务还得让大陆读者能直连投稿。站长平时也不用在线表格，为博客再维护一个服务，和一开始想省掉的麻烦很像。

**自己托管。** 自己跑个程序，就能把接口和文件都放在掌控之内。投稿随时可能进来，所以那台机器和网络得一直可用。站长不打算为了留言租服务器，也不想留一台闲置电脑常开。讨论到这里，博客一度回到了不能留言的状态。

## 从找地方放文件到用邮箱收件

后来站长问，能不能开个专门收留言的邮箱，本地工具能不能及时读到信？这正好补上了本地文件缺的那一步。电脑关着时，收件箱可以先接住留言。电脑开了，工具用常见的邮件协议把留言读进自己的文件，站长再慢慢决定哪些可以见人。

访客用的还是网页上的表单。表单发给 FormSubmit，由它把提交内容变成一封信，投到专用的 Neir 邮箱。我们先试了网页投稿和本地收信，再把审核过的内容接回 Jekyll。站长注册了这个专用邮箱，确认了投稿表单，日常收信和审核在本地窗口里处理。

## 浏览器寄出了什么

博文底部和 About 页共用一份 Jekyll 模板和一段 JavaScript。模板会把当前页面的路径放进表单所在的区域，比如 `/about/`。表单里只有昵称和正文。昵称最多 40 字，可以留空，展示时会写作「匿名」。正文必填，上限 2,000 字。按某条留言的「回复」会让下一次提交带上那条留言的编号。

每条投稿带一个由浏览器随机生成的 128 位 ID。即使昵称留空或者重名，站长也能按编号区分留言。邮件主题含有这个 ID，信里带一份可直接阅读的正文，也带一个给工具解析的 `comment_packet` 字段。浏览器把 `id`、页面路径 `article`、直接回复对象 `reply_to`、`nickname` 和 `body` 转成 UTF-8 JSON，再用 Base64URL 编码后放到这个字段里。

正式站点的表单要先确认收件地址。FormSubmit 会在确认邮件里给一个公开代号，Jekyll 用这个代号生成投稿地址。读者浏览器里看到的是这个地址，实际邮箱地址和应用密码由站长在本地工具里配置。[FormSubmit 文档](https://formsubmit.co/documentation)

试用时遇到过一次误报。留言到了，网页却说发送失败。FormSubmit 有时用 `text/html` 的响应类型返回 JSON，于是现在直接解析响应体，并同时识别布尔值 `true` 和字符串 `"true"`。超时或读不到明确结果时，网页显示「送达待确认」，在当前浏览器会话里保留正文和编号。正文、昵称和回复对象相同就会沿用原编号，本地收信时就算见到两封邮件，也只会把这条留言导入一次。[表单脚本](https://github.com/achmli/achmli.github.io/blob/master/js/post-comments.js)

## 本地收信、存档和预览

审核工具是用 Python 和 Tkinter 写的。Windows 上可以打开仓库里的 `_tools/blog_comments/open-comments.cmd` 启动。工具会先构建一份本地预览，从生成的页面中找出带留言区的路径和标题。About 同样按自己的路径被识别，审核列表里可以搜这个页面名。

站长用 Neir 的应用密码连接加密的 IMAP 接口。工具只读打开收件箱，每轮检查后等约八秒再查。它按主题找留言信，核对留言数据和主题里的 ID，再检查字段、长度和页面路径。收进来的留言先进入「待审核」。记录里的时间是导入的时间，网页展示时按上海时区格式化。[Neir 邮件客户端文档](https://neir.io/mail-clients)

私有档案在 `%LOCALAPPDATA%\AchmliBlog\comments\comments.jsonl`，一行一条 JSON 记录，可以拿文本编辑器打开。文件量小，工具每次保存会把所有记录写到临时文件，写完再替换档案。收信和审核共用一把进程内的锁，适合一次开一个审核窗口。

点「公开到预览」后，当前记录会被标为公开。预览页打开时会定期从本机读取结果，审核工具也会生成仓库里的 `_data/comment_threads.json`。这个文件用页面路径作键，每页下面是一组 `root` 和 `replies`，也就是主留言与回复列表。导出记录只带展示所需的数据，例如编号、昵称、正文和时间。新文章用同一份模板，等有留言获准公开，导出文件才会多出它的路径。

正式站点构建时，Jekyll 把当前页面的那份公开留言嵌进 HTML。浏览器用 `textContent` 插入昵称和正文，所以留言里的 HTML 会当作文字显示。读者打开已发布的页面就能读留言，投稿时才会走邮件链路。[本地审核工具](https://github.com/achmli/achmli.github.io/tree/master/_tools/blog_comments)

## 回复摆两层就够了

站长要的效果是主留言一层，回复一层。回复某条回复时，依旧放在同一个主留言下面，旁边标明「回复 某某」。比如 B 回复 A，C 再回复 B，那么 A 是主留言，B 和 C 在同一级，C 的旁边会标出 B 的昵称。

本地记录同时留了 `reply_to` 和 `root_id`。前者指向直接回复对象，后者指向整串讨论的主留言。工具会确认被回复的留言曾经公开过，而且两条留言属于同一页面。导出时，工具根据 `root_id` 把回复归到主留言下，再根据 `reply_to` 给回复的回复补上显示名。浏览器用导出的数据画出这两层。

## 删完怎样才会从网页消失

审核窗口能按页面、昵称和正文搜索。点「删除留言」会移除本地档案里的正文和昵称，留下编号和少量定位信息。只删掉整行的话，下一次重读收件箱，旧邮件就有机会被当成新留言收进来。删掉主留言时，工具也能用保留的编号给它留一个「原留言已删除」占位，让已经公开的回复留在原处。如果被回复的那条回复删了，更后面的回复仍能显示为「回复 已删除的留言」。

审核或删除完成后，工具会重生成公开 JSON。站长看过改动，再像发博文一样提交、推送，等 GitHub Pages 构建后，公开页面就会显示这一版列表。站长试过发一条、回两次、再撤下一条回复，最后在线上留下了一条主留言和一条回复。

留言审核通过前，正文只在邮件链路和本地档案里。已经公开过的正文即使从新版页面撤下，也可能还留在旧 Git 提交、原始邮件或读者保存的副本里。[GitHub 关于历史副本的说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 这套做法的代价

读者提交后，要等站长收信、审核并发布才能看到留言。表单关闭了验证码，公开前由站长逐条审核。收件箱仍可能收到垃圾邮件，审核量上来之后，逐条看也要花时间。

新留言仍依赖读者能连上 FormSubmit，以及邮件能送到 Neir。测试只确认了当时的网络环境，其他地区和运营商的情况还得看实际连通性。将来换服务时，投稿地址要重新配，未处理的邮件也要搬走。已经公开的留言随静态站点提供。本地的 `comments.jsonl` 则保留其他审核状态和删除记录，换电脑时需要把这份档案一起带走。
